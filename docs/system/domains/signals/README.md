# Signals

**Living file — update when this domain teaches you something.**
Covers: `backend/src/services/signals/`, `channels/`, `telegram/`.

## What it is

The ingestion side of the system. A Telethon-based Telegram reader listens to
configured groups and stores raw messages; a scan pipeline classifies each
message (new signal / edit / instant entry / limit order / logic keyword /
noise), parses it with per-channel deterministic regexes or learned rules,
and writes a signal row. A second layer decides *policy* per channel — trust
scorecards, pause state, learned parsing rules, and an AI recommendation of
which strategy that channel's signals should run. Separately, a Telegram
*bot* (Bot API, not Telethon) sends outbound trade alerts and accepts ~23
commands.

This domain **produces and resolves signal rows; it never places, modifies
or closes an order**. Bridge use here is read-only (`get_tick`).

## Where the code lives

- `services/signals/scan_messages.py` — the whole message-scan pipeline (`ScanCtx`): dedup, logic keywords, instant entry, SL adjustment, parse, staleness, strategy resolution, execution, alerting
- `services/signals/parser.py` — the gold-signal regexes: Format A ("Sell Gold 4520 - 4512"), Format B (`Direction`/`ENTRY`), Format C/GD2 ("XAU USD BUY NOW"), C3 limit-order layout, instant entry, learned-rule application
- `services/signals/scan_parse_classify.py` — one channel-agnostic classification/parse pipeline + DB recording
- `services/signals/scan_edit_reparse.py` — dedup/edit-correction state machine for Telegram edits (same message ID, new text)
- `services/signals/scan_staleness.py` — staleness guard (`max_signal_age_secs`) and per-channel strategy/skip-reason resolution
- `services/signals/resolution.py` — front half of `open_trade_from_signal`: gates + resolving strategy / lot size / stop loss (pure computation, read-only)
- `services/signals/pending_activation.py` — zone-fill watcher that activates pending signals when price re-enters the entry zone
- `services/signals/gap_revalidation.py` — the watcher noticing its own absence: marks every signal that was queued across a pause, an auto-execute toggle or a restart as needing re-validation before it may execute
- `services/signals/repo.py`, `tg_repo.py`, `commentary.py` — signal CRUD, `vantage_tg_signals` reads/writes, AI commentary JSON
- `services/signals/contradiction.py` — pure resolver for buy/sell contradictions BETWEEN sources (channel vs engine, channel vs channel); `contradiction_log.py` + `contradiction_log_repo.py` record what each policy would have done, behind `tg_contradiction_log_enabled`, and decide nothing — plan and stage 2 in [docs/todo/signals/010](../../../todo/signals/010-buy-sell-contradictions.md), owner questions in [simon-handover/041](../../../simon-handover/041-two-sources-say-buy-and-sell-at-the-same-time.md)
- `services/channels/strategy_ai.py` — Claude-backed per-channel strategy recommender (30-min Sonnet cycle; per-signal Haiku call)
- `services/channels/rule_generator.py` — auto-generates deterministic regex parsing rules from an approved AI-recovered signal
- `services/channels/repo.py`, `parser_repo.py`, `learned_rules_repo.py`, `unrecognised_repo.py`, `performance.py` — channel config, parser config, learned rules, unrecognised queue, scorecards
- `services/telegram/reader.py` (+ `reader_auth.py`, `reader_listener.py`, `reader_common.py`) — Telethon auth state machine, group listeners, message pipeline
- `services/telegram/bot_loop.py`, `bot_dispatch.py`, `bot_readonly.py`, `bot_infra.py` — getUpdates long-poll loop, command routing (`BotDeps`), read-only/toggle commands, process/env commands
- `services/telegram/alerts.py` — outbound Bot API trade notifications
- `services/telegram/keywords.py`, `keyword_triggers.py` — the six Logic Keyword lexicons and their trigger handlers

## Constraints / must not change

- `signals/` must never place, modify or close an order.
- No broker imports in the `telegram/` package; `keyword_triggers` closes trades only through an *injected* callback.
- The four bot commands that can place/close/restart (`/close`, `/marketbuy`, `/marketsell`, `/restartapp`) arrive as injected callables — their bodies stay on the runtime.
- `ai_fallback_fn`, `queue_unrecognised_fn`, `close_trade_fn`, `find_and_apply_instant_followup_fn`, `is_trading_paused_fn` are *required* injected collaborators with no real defaults — their implementations need context only the caller has.
- `rule_generator.py`: AI-generated content is only regex *pattern strings* stored as JSON — no AI-generated code is ever executed, and a rule is not saved unless it passes a self-consistency check against the human-approved values (tolerance 0.011).
- Logic keyword decisions (confirmed with owner 2026-07-22): CLOSE ALL closes only the triggering channel's own most-recently-opened trade, never every open trade; TP HIT is log/notify only, never moves SL or closes anything.
- `keywords.py` `limit_orders` is a reference list only — it feeds the AI-fallback gate and nothing else; editing it does *not* change the limit-order regex in `parser.py`. **`buy_orders`/`sell_orders` are different since 2026-08-27**: they are live bare-direction triggers (see Known things).
- `bot_loop.py`: only one process may long-poll a bot token; the authority check + 409 back-off stops paired Mac/VPS installs kicking each other in a loop. One pooled `httpx` client for the loop lifetime.
- The collaborator binding on `ScanCtx` is asserted by `tests/core/test_scan_messages_relocation.py`.

## Known things & gotchas

- **`status` records how a signal ENDED, not whether it worked (2026-09-23).** The four values the screens see are active, closed, expired and cancelled, and `closed` carries no information: a signal that took 300 dollars and one that gave back 300 both read it, which is 532 of the owner's 608 rows. The outcome is the net profit of the trades that signal produced — `vantage_simulated_trades`, keyed by `signal_id` — and `services/signals/outcomes.py` is the only place that turns those rows into a word. It is attached to the existing `repo.get_signals()` read rather than served separately, so the Dashboard's feed and the Trading tab's Signals table cannot disagree about the same signal. Three rules it is careful about: break-even is `flat` and not `won` (otherwise every scratch trade inflates the hit rate), an open trade has no outcome at all (running profit is not a result), and a signal whose legs are not all closed is left unresolved rather than reported on its closed half. One grouped query per read, pinned by a test — a lookup per signal would be 608 round trips into SQLite on every ten-second poll.
- **A cancelled signal can still have a winning trade.** Three do, in the owner's database: the signal was withdrawn after the position had been taken. Anything rendering a verdict must prefer the OUTCOME over the status, or it hides real money behind "skipped".
- **`vantage_simulated_trades.net_pnl` is `REAL NOT NULL DEFAULT 0`.** There is no "unknown P&L" row to defend against, so a guard for one is dead code. The consequence to watch is the other way round: if that column is ever relaxed, a gap in the record starts arriving as `0.0` and gets classified as break-even.

- **A terminal branch that records nothing is re-run forever, and "just record it" is not automatically the fix (2026-09-05, bugs/015).** The bare-direction branch of `classify_and_parse` was the one terminal path recording nothing, so the scan loop re-parsed the same message about once a second for as long as it stayed in the reader's fetch window -- 8,319 times for one 15-character SELL. The obvious fix, a parked `vantage_tg_signals` row, is wrong twice: the follow-up matcher reads `vantage_second_message_holds`, never that table, so the row helps it not at all; and `scan_messages.py`'s dedup probe routes any message that HAS a row into `_handle_signal_edit_impl`, where an edit adding full levels executes **only** when the status is `pending_followup` -- so a row parked under any other status turns a taken trade into a missed one. **Check what a row's mere existence changes before adding one to this table.** What shipped instead is an in-process, read-only guard keyed on the id AND a digest of the body, sitting below the learned-rules parser and the second-message block. Keyed on the body because a Telegram edit keeps the id and changes the text, which is how one of these becomes a real signal; read-only because a probe that records would suppress the first sighting's own log line. Whether these messages should be recorded at all is `docs/simon-handover/027`. Pinned by `tests/core/test_bare_direction_rescan_work.py`.
- **The same forever-relogging bug lives in every `continue` above the dedup probe (2026-09-18, bugs/065).** 015 was fixed in `classify_and_parse` and nobody checked the sibling branches. `scan_messages.py`'s `exclude_high_risk` gate `continue`s ~45 lines ABOVE `_tg_repo.get_tg_signal_meta`, so it records nothing either: nine parked messages wrote **204,359 identical INFO lines in 7.5 hours — 80% of that day's 31MB log**, the oldest of them from a previous session. Fixed with 015's own idiom (`_note_high_risk_skip`, bounded OrderedDict of 512, keyed on id + body digest, `reset_high_risk_log_memory()` seam), log half only, for 015's own reason. **Anything that `continue`s before that dedup probe re-runs about once a second, forever** — the gates above it now are Logic-Keyword media/forwarded skips, CLOSE ALL, RISK FREE/BE, the slot filter and the parser-disabled check. Before adding another, decide what makes it stop.
- **`exclude_high_risk` is a substring match on the whole body.** `"high risk" in text.lower()` — so a signal that only mentions high risk in passing is dropped identically to one labelled `HIGH RISK TRADE` (live: VIP `21426` "lower entry high risk is 4355-4350 Zone", `21427` "If you took the high risk set up well done"). Whether it should match only a label line is open for the owner.
- **The Telegram decision log records; it decides nothing (2026-09-18, signal-validation/010).** `signals/decision_log*.py` writes one row per signal reaching an execution decision, on both the full-signal and IME paths, plus what four currently-off gates would have decided. Three things about it are load-bearing. **It writes to `reversal_engine.db`, not the core DB** — the core DB is per-environment, so a corpus kept there splits in half the day the account switches (`pro_corpus_repo` learned this on 2026-08-06 with a live table of zero rows); `account_env` is a column instead. **Every fact is gathered before any gate returns** and carried to whichever exit is taken — `reversal_engine_live_execute` states the rule: recording at each early return logs "would take" for a variant whose later gates never ran. **An unavailable fact abstains (NULL), never False.** The sweep rides `core_signal_snapshot.run_snapshot_cycle` as a fourth cadence rather than a new loop, because `runtime.py` is at its LOC baseline and shrink-only. Nothing hooks the close path. **A fact read live and a fact replayed are different things and the code treats them differently**: the HTF bias is a live read, so it abstains outside `MAX_BIAS_LAG_S`; the entry trigger replays `candles_range` ending at `decided_at`, so it has no age limit at all — which is what makes `decision_backfill` (rebuilding decisions from past closed trades, marked `source='backfill'`, executed-only, idempotent) worth running. Readout on the Parsing page via `telegram_controller`; neither table is pruned, deliberately — see signal-validation/010.
- Telegram delivers an *edit* as the same message ID with new text; `scan_edit_reparse.py` can **flatten (close) a real open position** via `close_trade_fn` when an instant-entry edit flips direction.
- **The REF backfill is a second copy of the parser pipeline, and it drifted (2026-09-16, bugs/061).** `core_ref_signal_backfill.parse_stored_message` is a side-effect-free reparse of stored messages; its docstring claims it mirrors `classify_and_parse`. It was written 2026-07-31 and still branched on `parser_format` a month after the live path stopped, and its `try`/`except` sat around the whole loop AND the single INSERT after it, so one `ValueError` from `parser._f` discarded every record already built and skipped every later message. One Gold Diggers Scalping message typing its entry as `4284.5. - 4278.5` cost 15 REF signals an hour for two days, visible only as a one-line WARNING. Both halves fixed: a per-message guard (the live scan has had one since the 2026-08-25 merge) and one pipeline for every channel here too. **Whatever changes in `classify_and_parse`'s deterministic half has to change here as well** — there is no gate that would tell you.

- **Parsing is channel-agnostic (2026-08-27, owner directive).** `classify_and_parse` no longer branches on the channel's configured `parser_format` at all: every channel runs learned rules -> second-message merge -> limit-order layout -> currency guard -> Format A/B -> GD2 -> partial -> bare trigger -> AI fallback -> unrecognised queue, in that order. Before this, a `format_ab` channel never ran a single GD2 regex and a `gd2` channel never ran Format A/B, so a well-formed signal in the "wrong" layout for its channel was dropped. `parser_format` still does two things and only two: `'none'`/disabled stops the channel being scanned, and it sets the DEFAULT for that channel's Immediate Market Entry flag.
- **Immediate Market Entry is channel-agnostic too (same change).** The scan path used to pick the trigger parser from `parser_format`, and the non-gd2 one requires a literal `XAU… BUY NOW`. So on Gold Diggers VIP a market entry worded "Buy Gold Now" / "Buy Zone Now" / "XAU USD BUY" matched nothing at all, while the identical message on a gd2 channel fired. Both trigger parsers now run for every channel, with no substring pre-gate.
- The limit-order format ("BUY/SELL LIMITS GOLD @ … AREA") is checked *ahead of* every parser, so it fires for any channel (explicit 2026-07-22 decision). **It is still the only thing that places a genuine resting broker order** — every other zone signal is a Python-side wait that fills at market. Whether that should change is Simon's call: [008-zone-signals-and-real-pending-orders.md](../../../simon-handover/008-zone-signals-and-real-pending-orders.md).
- **A signal row's `source_name` is decorated** — `Telegram Auto (<channel>)` — while `channel_performance` / `channel_strategy_rec` / `channel_parser_config` are keyed on the bare name. `channels/repo._canonical()` strips that wrapper generically since 2026-08-27; before that it only knew the two decorated strings hardcoded in `CANONICAL_CHANNELS`, so any third channel's Channel Strategy pick was silently ignored everywhere a stored signal was read — expiry ladder, grid dispatch, `open_trade_from_signal`'s own strategy resolution, per-channel schedule windows.
- **The pending watcher's momentum check reads a cache nothing cleared.** `runtime._dpm_candles` was refreshed only while a trade was open, so once the last position closed it froze at that bar — and the watcher defers any signal whose direction disagrees with the last candle it is handed. A frozen bearish bar deferred every queued BUY until it expired. `monitor_cycle` now refreshes it whenever the watcher will read it, and clears it on a failed fetch.
- **A pause does not age the queue; it freezes it (2026-09-11, owner).** `monitor_cycle` skips the pending watcher entirely while trading is halted, so for the length of a circuit breaker or a daily-loss halt nothing in the queue expires or is re-checked, and signals keep arriving into it: the scan path queues a signal whose price is outside its zone, and one whose price is INSIDE its zone is refused by `open_trade`'s pause gate and put back to 'pending' by `scan_auto_execute`'s failure handler. On resume the whole backlog runs in one pass. The expiry ladder culls the short windows, but a template signal has an hour and a runner signal has four — so hour-old setups were executing on the first tick that touched their zone, judged only by gates that ask about *now* (news, bias, schedule). `gap_revalidation.py` closes it: any signal in the queue when the watcher returns from an absence longer than `GAP_THRESHOLD_S` must face `check_pre_trade_filters` against the current price, with **none of the four local bypasses** (grid template, self-managed strategy, EA template, IME) and with the IME arm of `governor.rr_filter_bypassed` suspended. Suspending that arm is what makes the gate bite: IME is on globally, so without it the R:R test is skipped inside the filter for every configured Telegram channel and the re-validation would be inert for exactly the signals it exists for. The static `RR_BYPASS_SOURCES` channels keep their exemption — they bypass because they supply their own levels, which staleness does not change.
- **The last-run time lives in `app_config`, not in module state**, because a restart is one of the gaps this catches and module state does not survive one. It is stamped at most every 15s against a 1-5s watcher cadence, so the measured gap runs up to that much longer than the true one — the safe direction, and the reason the 60s threshold sits well clear of the 5s idle poll. No stamp at all (a fresh install, a fresh test DB) reports no gap: an absent record is not evidence of an absence.
- **That momentum check had never run on this account (2026-09-21, owner report).** It reads DPM's M5 candle cache, and `monitor_cycle` only fills that cache when `dpm_enabled`; this account has it at 0, so the list is permanently empty and the `if dpm_candles and ...` branch has never executed. It is the only gate in the release path that makes a BUY and a SELL mutually exclusive on the same tick, and on the 14:22:41 resume below that is what let both out. `pending_momentum_gate_enabled` (migration 51, OFF) feeds it into a **local** list in `monitor_cycle`, never through `set_dpm_candles`: the shared cache is also read by the Auto strategy picker (`resolution.regime_from_candles`), the trailing ADX and the resting-order sweep, and one toggle must not change four behaviours. Pinned both ways by `tests/positions/test_momentum_gate_feeds_the_watcher.py`.
- **The re-validation asks about *now*, never about the *spread* of the release (2026-09-21, owner report).** The gap mark above worked exactly as designed on a resume from the daily-loss halt — `away 3745s, 5 queued signals must re-validate` is in the log — and three of the five then opened inside 700ms: BUY @ 4362.33, SELL @ 4361.82, BUY @ 4361.85, ages 3149s / 2695s / 1388s, stopping only at `max_open_trades = 3`. Every gate it suspends the bypasses for passed, because each asks a question about the present instant and none asks how far the release has drifted or whether it is about to empty in both directions. Three guards now cover that, all OFF (migration 51, `services/signals/stale_release.py`).
- **`price_in_entry_range` rationalises both directions at one price, and the asymmetry is the reason.** A SELL fills at any bid ≥ `entry_low`, unbounded, as an "equal or better fill" — the 2026-09-21 SELL sold 7.17 pts above a zone topping out at 4354.65. The *chase* side has a cap (`scan_auto_execute.MAX_GAP_FIRE_PTS`, 15.0) and the better side had none, so IME gap-fire dragging two BUY zones up to 4362.38 and a stale SELL taking a "premium" 7 pts up converge on the same price. `stale_better_fill_cap_*` caps the favourable side at the same number and the same boundary (`excess <= cap`, matching `0 < gap <= MAX_GAP_FIRE_PTS`); `stale_release.BETTER_FILL_CAP_PTS_DEFAULT` is asserted equal to it so the pair cannot drift. Applied in the pending watcher only — for a signal taken on arrival the better price genuinely is better; for one queued 45 minutes it is a different setup.
- **Nothing compared the released signals to each other.** `contradiction.py` is shadow-only by design, and `positions/core_internal_exposure_guard.py` is called only from the Reversal and Breakout live-execute paths and excludes Telegram sources outright — so the pending watcher asked nothing. `burst_hedge_guard_enabled` refuses a direction opposing one already released **in the same pass**, deliberately not one already on the book: widening it to open positions would re-fight the exposure guard's measured OFF decision (opposing legs were 19% of the Reversal Engine's closed trades and ~80% of its profit) for every source at once.
- **The BUY/SELL Orders boxes are live triggers (2026-08-27, reported live).** GOLD DIGGERS INSTITUTIONAL sent "PREPARE FOR A BUY" with that exact phrase saved in the BUY Orders box and the app did nothing — it could not have. `buy_orders` fed exactly one thing, the allow-gate in front of the AI fallback, so a phrase typed into it bought permission to spend an AI call and nothing else; direction detection lived entirely in `parser.py`'s per-format regexes. There was no `sell_orders` box at all, so the feature could only ever have worked one way. Both boxes now drive `keyword_triggers.parse_lexicon_direction_trigger`, which returns the same `(direction, None)` shape as the built-in bare triggers and takes the same path: market entry when IME is on for that channel, held quietly otherwise. Every channel, like every Logic Keyword.
- **That trigger matches per-LINE and exactly — not as a substring**, unlike every other lexicon here, and it refuses any message containing a digit. These phrases become market orders: as substrings they would fire on most of what a gold channel says in a day, and the no-digit rule keeps anything that states a level with the per-format parsers, which will use those levels rather than ignoring them. A message naming both directions is refused rather than guessed at.
- **No shipped default is a single bare word** (owner directive, after `BUY`/`SELL` shipped briefly). Line-exact matching stops a one-word phrase firing on a *sentence*, but not on a channel posting a lone `BUY` as commentary — which is not distinguishable from one posting it as an instruction. Every default names the pair, the zone or the action. A bare word is still addable in the UI; it just cannot arrive by default. Pinned by `test_no_shipped_default_is_a_single_bare_word`.
- `DEFAULT_LEXICONS` is only the fallback for a category with no saved row. **Editing a default does not change an install that has already saved that box** — and the Parsing tab's Save writes every box at once, so any install that has ever pressed Save has its own copy of all of them.
- `keyword_triggers.AI_FALLBACK_GATE_LEXICONS` names the lexicons the AI-fallback gate combines. Two tests had gone stale enumerating three of them by hand; derive from that constant instead.
- The Logic Keywords boxes on the Parsing tab are rendered from `DEFAULT_LEXICONS`, not a hand-written tuple — a box missing from the UI is now a *trigger nobody can turn off*, not just an uneditable list. Pinned by `tests/frontend/test_parsing_settings_render.py`.
- Parser tolerances are deliberate: non-breaking spaces, optional colons, en/em-dash/slash/"to" range separators, widened currency capture so `XAU/USD` isn't truncated and wrongly rejected.
- `max_signal_age_secs` (formerly hardcoded 4 min) is an Expert Tunable — older signals are recorded as *historical* and never executed.
- Group IDs are remapped by name in `channels/repo.py` (Telegram-side renames keep the same group_id).
- `bot_offset` is persisted to `app_config` so a restart doesn't re-run commands like `/restartapp`.
- `strategy_ai.py` regime thresholds are XAUUSD-specific and hardcoded in-module (session windows, ADX/ATR bands per strategy).
- `scan_messages.py` still carries one piece of engine coupling: `engine_for_eval`, threaded to `evaluate_signal_strategy`.

- **One channel had two strategies, and the difference was which route reached the broker first (2026-09-21, owner-reported).** `channels/repo._canonical()` had already made both spellings one channel, and `channel_performance` held one row — so this was not a naming bug. It was a *precedence* bug. `signals/resolution.py` resolved "active Trading Schedule window override > Channel Strategy pick"; six other routes to the broker — `trading/instant_entry`, `trading/instant_followup`, both lookups in `trading/limit_order_signal`, `signals/pending_activation._resolve_effective_strategy` and `positions/core_grid_template_dispatch.grid_template_for_source` — called `get_channel_strategy_override()` alone and never saw the window at all. With the schedule holding `template:30 TP1 SL50 and Trail` on all seven days and the channel holding `template:GD Instituational - single`, GOLD DIGGERS INSTITUTIONAL ran **both** on 2026-09-21: different geometry, different stop, different lot, chosen by nothing but which path got there. Owner's call: **the window wins everywhere.** The precedence now lives once, in `risk/schedule.effective_channel_strategy()`, and `schedule_source_key()` carries the engine-name mapping that went with it. `tests/core/test_one_strategy_per_channel.py` holds both halves — that it resolves the chosen way, and that no route asks the channel layer directly. **A seventh route that reads `get_channel_strategy_override` on its own re-opens this**; the test names each route, so add yours to it.
- **A window that has a source *disabled* has no opinion about its strategy.** `_resolve_source_gate` returns `(False, None)` and `effective_channel_strategy` then falls through to the channel pick. Stopping a source trading is `check_trading_schedule`'s job, and conflating the two would turn a stand-down into a strategy. Unchanged by the consolidation, and now pinned.

- **Telegram signals now reach the cross-engine signal bus, and the readers had to be taught not to see them (2026-09-21).** `signal_bus` carried engine rows only, so the only contradiction anyone could observe was engine-vs-engine. Putting channel signals on it is what makes channel-vs-engine and channel-vs-channel visible at all — and is also how you would silently break live trading, because `has_conflict_on_bus` is a **suppression gate** and the breakout engine reads it over a **six-hour** window. One Telegram SELL becoming visible there would cancel engine BUYs for the rest of the day, with nothing in the logs saying why. So `get_concurrent_signals` gained `kinds=`, defaulting to `(KIND_ENGINE,)`, and a NULL `source_kind` coalesces to `engine` because every pre-existing row was one. The 25 tests in `tests/core/test_signal_bus_repo.py` pass unmodified; that is the proof, not the new ones.
- **The bus has no symbol column and never did**, so a BUY on one instrument already counted against a SELL on another. Added, but the filter is **opt-in** (`symbol=`), and a NULL symbol matches everything — only legacy rows have one, and an instrument nobody recorded cannot be ruled out. Narrowing the live gate by treating NULL as a non-match would have been the invisible half of this change.
- **A Telegram bus row's `engine` column is the CHANNEL NAME, not the literal `"telegram"`.** Every reader excludes on that column, so a shared value would make each channel exclude every other channel — deleting exactly the contradiction the feature exists to see.
- **`freshest wins` abstains on every contradiction today, and that is correct.** The bus records whether a signal is still *open*, which is not whether it has *filled*, and only that one policy needs the difference. `contradiction.Active.is_pending` is `Optional[bool]` with no default so a caller has to state which of the three it means, and an unknown produces `UNKNOWN` (stored as NULL), never an allow. Same rule as `decision_shadow.decide`. Recording fill state means a write on both engines' execution paths — stage 2, and it needs sign-off.
- **A source never contradicts itself in `contradiction.py`.** A channel flipping direction is a correction, and `scan_edit_reparse.py` already owns that (it can close a real position). An engine holding both sides is `positions/core_internal_exposure_guard.py`'s question, answered OFF by default on measured evidence: opposing reversal legs were 19% of closed trades and ~80% of the profit. Folding either in here would re-fight a decision already made with data.
- **With the study's toggle off, a Telegram signal is not written to the bus at all** — not merely unread. "Off" for anything that touches `signal_bus` has to mean the table looks exactly as it did before the feature existed. Pinned by `test_with_it_off_the_signal_never_reaches_the_bus_either`.
- **Both engine services sit one line under the 800-line LOC gate.** The observe call is a named helper (`contradiction_log.observe_engine_signal`) for that reason alone; inlining the same six lines twice took both files to 804 and failed the gate on the first run.

- **The first gate came off the shadow bench on 2026-09-21 (Stage 2).** `capability_gates.tg_event_tier_blocks` now refuses a Telegram entry inside a scheduled-event window, on BOTH order paths — the fifth gate `instant_entry.py` has to keep its own copy of, because it never calls `resolve_open_trade_params`. It has **its own** switch, `tg_event_tier_gate_enabled`, and not the existing `event_tier_gate_enabled` that the Reversal Engine's live path reads: one switch arming two engines destroys the attribution the whole staged plan exists for. The tier windows stay in `event_tiers.Config` — one definition, two independent decisions about who honours it. Off by default, migration 50, and the full reasoning (including why `confirmed entry`, which has the only positive P&L in the shadow record, is NOT the one to promote) is in [docs/todo/signal-validation/020](../../../todo/signal-validation/020-stage-2-the-event-tier-gate.md).
- **A promoted gate stops being a challenger.** Once `tg_event_tier_gate_enabled` is on, the `event tier` shadow variant and the live champion agree by construction, because the live path is now doing what the variant was recording. That is the report working, not a bug in it.
- **Off must read nothing, and the order matters.** The switch is checked before the calendar, not after. `news_calendar.get_events` can reach the network, and a gate that reads first is indistinguishable from one that is on, on any trace of the order path — which is the only way anybody can say afterwards what was actually running.
